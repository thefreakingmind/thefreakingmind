# 🧠 How I Think About Engineering

I care less about simply making something work and more about understanding **why it works**.

When designing systems, I usually think through:

```text
Requirements
    ↓
Architecture
    ↓
Failure Modes
    ↓
Data Flow
    ↓
Consistency
    ↓
Scalability
    ↓
Observability
    ↓
Security
    ↓
Cost
    ↓
Developer Experience
```

Some questions I constantly ask:

* What happens when this component fails?
* What happens when traffic increases 100x?
* Can we replay the event?
* Can we recover without manual intervention?
* How do we observe this system?
* Where is the source of truth?
* What happens during a regional failure?
* How do we migrate without downtime?
* What happens when the database becomes unavailable?
* Can this architecture be operated by a small team?
* What will this cost at scale?

# 📚 Engineering Philosophy

### Build simple systems first.

Complexity should be earned.

### Automate repetitive work.

If a human has to repeatedly perform the same operational task, there is probably an opportunity to automate it.

### Observability is not optional.

If you cannot understand what your system is doing, you don't really control it.

### Distributed systems are about failure.

The interesting question isn't:

> "What happens when everything works?"

It's:

> **"What happens when everything goes wrong at the same time?"**

### Infrastructure should enable engineers.

The best platform is one that makes the correct thing the easiest thing to do.

### AI should augment engineers.

I'm interested in AI systems that make engineers dramatically more capable—not systems that simply replace a text box with another text box.
